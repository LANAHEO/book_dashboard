# 서점 파서 점검

Book Radar는 교보·예스24·알라딘의 HTML과 API를 긁는다. 서점은 예고 없이 바뀌고,
빈 응답을 200으로 돌려주기도 한다. 이 스킬은 "이상하다"는 보고를 **원본에서 확인한
사실**로 바꾼다.

## ① 언제 켜나

**켠다**
- 순위·출간일·항목 수·링크·갱신 시각이 틀렸다는 보고
- 특정 서점 목록이 안 나오거나 상위권이 비었다는 보고
- 서점 페이지 구조를 조사해야 하는 작업

**켜지 않는다**
- 새 기능 설계·UI 작업·배포 (증상 보고가 없는 경우)
- 파서와 무관한 Supabase·스케줄러 단독 문제

## ② 무엇을 읽나

**읽는다**
- `server.js`의 해당 서점 파서(`mapKyoboItem` / `mapYes24Block` / `mapAladinBlock`)와
  수집 함수(`fetchKyoboData` / `fetchYes24List` / `fetchAladinList`)
- 소스 정의 (`sourceUrl`, `ttlMs`, `pages`, `limit`)
- 라이브 응답: `/api/dashboard`
- **서점 원본** (HTML 또는 API)

**읽지 않는다**
- 무관한 UI·CSS
- 커밋 로그 (원인을 추정하는 용도로만, 근거로 쓰지 않는다)

## ③ 순서

1. **증상을 숫자로 고정한다.** "안 나온다"를 "95개여야 하는데 46개, 1~50위가 없음"으로
   바꾼다. 숫자가 없으면 고쳤는지 알 수 없다.
2. **우리 응답을 본다.** `/api/dashboard`에서 해당 목록의 `itemCount`, 순위 최소·최대,
   `warning`, `error`, `stale`.
3. **서점 원본을 직접 가져온다.** 그리고 **파서의 정규식을 그 원본에 직접 돌려본다.**
   추측하지 말고 몇 개가 매칭되는지 센다.
4. **로컬과 운영을 비교한다.** 둘은 Supabase의 `dashboard_snapshots` 한 행을 공유하므로,
   나중에 수집한 쪽이 상대를 덮어쓴다. 로컬 수정이 반영 안 된 것처럼 보이면 이걸 먼저 의심한다.
5. 필요하면 **브라우저로 실측**한다 (Playwright: `~/.claude/skills/gstack/node_modules/playwright`).
6. **원인을 분류한다.** 아래 넷 중 하나로 답한다.

## ④ 도구로 가져올 것 vs 내가 판단할 것

**도구에서 가져온다 (추측 금지)**
- 서점 원본 HTML·JSON, 정규식 매칭 개수, 렌더된 화면, HTTP 상태·헤더
- 항목 수, 순위 범위, 날짜 문자열 — 전부 실제 값

**내가 판단한다**
- 원인 분류, 고칠지 말지, 어디까지가 이번 범위인지

## ⑤ 결과물 양식

```
증상:      <숫자로. 기대값 대비 실제값>
우리 응답: <itemCount / 순위 범위 / warning / stale>
서점 원본: <블록 수, 정규식 매칭 수, 원문 발췌>
원인:      <파서 / 서점 변경 / 일시적 응답 / 측정 오류> 중 하나
근거:      <위에서 확인한 사실만>
조치:      <고침 · 안 고침 · 관찰 필요> + 이유
```

## 이 프로젝트에서 이미 겪은 함정

새로 조사하기 전에 여기부터 본다. 전부 실제로 발생했다.

| 함정 | 증상 | 실제 원인 |
|---|---|---|
| 공유 스냅샷 | 로컬 수정이 반영 안 됨 | 운영이 같은 Supabase 행을 덮어씀 |
| 부분 수집 | 51~100위만 나옴 | 한 페이지가 빈 200 응답, 예외가 아니라 "적은 성공" |
| 월 단위 날짜 | 출간일이 전부 `.01` | 원본에 일자가 없고 정규화가 1일로 채움 |
| 순위≠쪽 | 딥링크가 엉뚱한 쪽 | 서점 API 순위와 웹 페이지 배열이 다름 |
| 짧은 목록 | 경고가 상시 표시 | 분야별은 원래 30개, 뒤 페이지가 비는 게 정상 |

## ⑥ 검증 — 답하기 전에 확인

- [ ] 서점 **원본을 직접** 가져왔는가 (우리 API만 보고 결론 내지 않았는가)
- [ ] 정규식을 원본에 실제로 돌려 매칭 수를 셌는가
- [ ] **측정 도구 자체를 의심했는가** — 이 프로젝트에서 측정이 세 번 틀렸다:
      짧은 제목을 건너뛰는 가드, 추천 영역 링크까지 세기, `innerText` 매칭 실패.
      결과가 이상하면 대상보다 **측정을 먼저** 의심한다.
- [ ] 정상 케이스에서 오탐이 나지 않는지 확인했는가 (짧은 목록·비도서 필터)
- [ ] 로컬/운영 스냅샷 공유를 고려했는가
- [ ] 숫자를 하나라도 추측해서 쓰지 않았는가

## ⑦ 안전장치

- **서점을 두들기지 않는다.** `fetchText`의 호스트당 4개 제한을 우회하지 않는다.
  조사용 반복 요청은 간격을 두고 최소 횟수만.
- **지우지 않는다.** `rank_history`·`dashboard_snapshots`·`source_snapshots`를 삭제하지
  않는다. 캐시 무효화가 필요하면 먼저 말하고, `.cache/rankings`의 해당 파일만 지운다.
- **비밀을 출력하지 않는다.** `.env` 값, `SUPABASE_SERVICE_ROLE_KEY`를 화면에 찍지 않는다.
- **운영을 먼저 건드리지 않는다.** 로컬에서 재현한 뒤에 운영을 확인한다.
- 원인이 "서점 변경"이면 고치기 전에 무엇이 바뀌었는지 사용자에게 먼저 보고한다.
